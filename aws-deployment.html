Secure multi-tier deployment on AWS

Deploying a web app and its database to AWS entirely from code, then reviewing my own setup for security weaknesses.

Type
RMIT coursework (DevOps), individual
Year
2026
Tools
Terraform, AWS (EC2, VPC, Application Load Balancers, S3), Ansible, Docker, GitHub Actions, Bash, PostgreSQL

The problem

The app had a frontend, a backend and a Postgres database. Setting this up by hand in the AWS console is slow, easy to get wrong, and hard to repeat. The goal was to build the whole environment from code so it could be created, changed and destroyed reliably, without exposing the database or the servers to the internet.

Objectives

  • Create all AWS infrastructure with Terraform, with no manual console changes.
  • Keep the database and backend away from direct internet access.
  • Run the frontend and backend across two availability zones so one zone failing doesn’t take them down.
  • Deploy automatically from GitHub without putting credentials in the code.

How I built it

  1. Built it in stages. I started with the backend and database on one EC2 instance, added the frontend, then moved each container onto its own server, and finally scaled out with load balancers. Each stage is saved as a git tag (section-a to section-c).
  2. Network. Terraform created a VPC, two public subnets in different availability zones (an Application Load Balancer needs at least two), an internet gateway, a route table and security groups. The Ubuntu 24.04 AMI is looked up with a Terraform data block instead of being hard-coded.
  3. Servers and load balancers. Five t3.micro EC2 instances: two frontends and two backends (one of each pair in each zone) and one database. A public Application Load Balancer on port 80 sends traffic to the frontends, and an internal one (internal = true) on port 8080 sends traffic to the backends. Each load balancer health-checks / and stops sending traffic to a server that stops answering.
  4. Locking down traffic. Every tier has its own security group, and each one only allows the security group in front of it: frontend servers only accept 8081 from the frontend load balancer, backend servers only accept 8080 from the backend load balancer, and the database only accepts 5432 from the backend servers. SSH is only allowed from the IP address of the computer running the deploy script.
  5. Shared state. Terraform state is kept in an S3 bucket, so my laptop and GitHub Actions work from the same state. Without it, the pipeline wouldn’t know the servers already exist and would try to build them again.
  6. Configuration. An Ansible playbook installs Docker on every server and starts the right container on each one with the community.docker.docker_container module. The frontends use the backend load balancer’s address as their backend URL, and the backends reach the database on its private IP, so that traffic stays inside the VPC.
  7. One-command deploy. A Bash script (deploy.sh, with set -e so it stops on any error) creates the SSH key and S3 bucket if they’re missing, runs Terraform, writes the Ansible inventory from the Terraform outputs, waits for each server to accept SSH, then runs the playbook. Running it again is safe, because Terraform and Ansible only change what is different.
  8. Automation. A GitHub Actions workflow runs the same script on every push to main (or manually). It uses six repository secrets: three for AWS, the SSH key pair and the database password.

Result

The full environment deploys from a single workflow run, and all 13 deployment runs passed. The site loads through the frontend load balancer, and opening a frontend server’s IP directly on port 8081 times out, which shows requests can only arrive through the load balancer. No AWS keys are stored in the code.

A problem I had to fix

After I pointed the frontends at the internal load balancer, both status checks on the site failed. The backend servers’ security group still only allowed traffic from the frontend servers, not from the new load balancer, so its health checks were blocked. I changed the rule to allow the backend load balancer’s security group instead, and the checks went green again about a minute later.

Security review of my own work

After finishing, I reviewed the code the way an attacker or auditor would. These are the weaknesses I found and how I’d fix them in a production setup.

IssueRiskFix
The Terraform variable for SSH defaults to 0.0.0.0/0. My deploy script narrows it to my own IP, but running Terraform on its own would not. Anyone on the internet could try to log in, which invites brute-force attempts. Remove the default so Terraform refuses to run without an IP range, or remove SSH and use AWS Systems Manager Session Manager.
All five servers sit in public subnets with public IP addresses (Ansible connects to them over SSH) Only the security groups keep the backend and database off the internet. One wrong rule would expose them. Move the backend and database into private subnets with a NAT gateway, and reach them through a bastion host or Session Manager.
Only one database server The frontend and backend survive losing a zone, but the database doesn’t. Use a managed database such as Amazon RDS with a standby in a second zone.
Database password written in docker-compose.yml (from the starter code, used for running locally, not in the AWS deployment) Anyone who can read the repository can read the password, and copied config often ends up in production. Pass it in from GitHub Secrets or AWS SSM Parameter Store at deploy time.
Deploy script falls back to a test password (local-test-password) if DB_PASSWORD isn’t set A missing secret silently becomes a known, weak password. Make the script stop with an error if the password isn’t set.

What I learned

  • Security groups that reference each other are a simple, strong way to control which servers can talk, but adding a load balancer means updating them, as my health-check problem showed.
  • Moving secrets out of the code is only half the job. Defaults and fallbacks can quietly undo it.
  • Remote state matters as soon as more than one place runs Terraform, including CI.
  • Reviewing my own work afterwards found problems that “it deploys and works” didn’t show.
