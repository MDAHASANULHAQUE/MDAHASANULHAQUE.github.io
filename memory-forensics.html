Memory forensics on a Windows system

Using Volatility 3 to find out what was running on a Windows machine from a copy of its memory.

Type
RMIT coursework (Computer and Internet Forensics)
Year
2026
Tools
Volatility 3 (Framework 2.28.2), Kali Linux 2025.2 in VirtualBox

The problem

Some malware leaves little or nothing on disk and only exists while the computer is running. A memory dump captures that moment. The task was to analyse a Windows memory image and work out which processes were running and which ones deserved a closer look.

Objectives

  • Set up a working memory forensics toolkit.
  • Identify the system the memory came from.
  • List running processes and find any that were hidden.
  • Check what suspicious processes had open and which DLLs they loaded.

How I investigated

  1. Setup. Installed Volatility 3 from source in a Kali Linux VM in VirtualBox, so the analysis ran in an isolated environment.
  2. Identify the system. Ran windows.info to confirm the Windows version and details of the image before trusting any other output.
  3. List processes two ways. windows.pslist follows Windows’ own list of processes. windows.psscan scans memory for process structures directly. Malware can unlink itself from the first list, so a process found only by psscan is a red flag.
  4. Cross-check with psxview. Ran windows.psxview, which compares several ways of finding processes side by side, to confirm what pslist and psscan showed.
  5. Check open handles. Ran windows.handles with --pid on processes of interest to see which files, registry keys and other objects they were using.
  6. Registry and DLLs. Listed the registry hives in memory with windows.registry.hivelist, and the DLLs a process had loaded with windows.dlllist.
  7. Save the evidence. Used -r csv and redirected the output to a file, so results could be kept and reviewed outside the terminal.

Findings

Comparing the two process lists and reviewing handles narrowed the investigation down to the processes worth reporting on.

Specific findings are left out because this was assessed coursework. I’m happy to walk through the method in an interview.

Why it matters for a SOC

When an endpoint alert fires, memory analysis can show what was actually running, even if the malware has removed its files. Knowing why pslist and psscan can disagree helps an analyst spot hiding techniques instead of trusting one view of the system.

Recommendations

  • Capture memory early in an incident, before rebooting or shutting down the machine.
  • Hash the memory image as soon as it’s collected, so its integrity can be proven later.
  • Use endpoint detection tooling that watches process behaviour, not just files on disk.

What I learned

  • Building the tool from source taught me more about its dependencies than a ready-made install would have.
  • Always confirm the system profile first. Every later result depends on it.
  • One plugin’s output is a view, not the truth. Cross-checking is what finds hidden activity.
